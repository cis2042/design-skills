# 规格审阅与行为验证

## 固定合同门禁

完整交付必须满足 [delivery-contract.md](delivery-contract.md)，固定七份 Markdown 和 delivery.json，必须包含计划任务与原任务源唯一映射。先检查任务依赖无环、所有功能与 Surface 有任务、前提/输入/产物/验收/验证齐备，再执行语义审阅及机器校验。

## 交付审阅

先逐模块记录三项主线的具体证据：功能详规、交互流程、界面结构。每项结论需指向相关章节并说明通过原因或缺口；不能用同一句“完整”批量签署。

- 全量范围有模块覆盖记录；每个模块有固定十项详规，非只有功能总表。
- 每个主页面和结构不同的子页有真实业务分区/线框；字段、操作、滚动和状态变化能直接交接。
- 核心流程图配逐操作转换表；不能把设计执行顺序当用户路径。
- 任务总表配可执行说明；对象、第一屏问题、业务字段、父页依赖、允许变化和动作去向具体明确。

- 每项功能有用户目标、对象、输入/输出和可观察验收；能找到对应页面与流程。
- 每个动作有触发、权限、状态变化和去向；危险副作用的批准和真正完成明确分开。
- 每个错误说明发生原因、当前数据/效果、用户可做什么；无恢复途径时说明责任方。
- 每个页面有明确内容分区、主次操作和返回路径；详情/向导未被无理由塞入一级导航。
- 全局入口、子视图、表单校验、结果面和重要状态均覆盖；通用控件没有机械扩展成整页。
- 流程中的 ID 均有定义；定义无重复；引用无断链；跨页跳转保留正确对象和作用域。
- 设计与实现事实有来源；旧截图、勾选、HTTP 成功、文件存在不充当运行证据。
- 冲突有依据和处置；没有仅凭日期更晚就覆盖用户确认的导航。
- 现行规格仍唯一；新增任务没有与已有任务重复或自动勾选。
- 多端约束来自用户：要求一致时不能以框架不同为由放宽外观/行为。

## 用于前向测试的场景

以下是测试输入和观察点，不是固定输出答案。可在隔离目录由另一会话执行；没有实际执行时不得宣称行为评测通过。

### 场景 A：有冲突的旧产品

输入：已确认导航“订单/客户/设置”；后写的原型 README 增加“删除订单”一级菜单；代码删除只返回演示成功；用户要求整理完整功能。

观察：保留确认导航，登记原型冲突；将删除操作归属订单详情/确认；把演示实现与目标删除结果区分；提供失败/权限/返回链。

### 场景 B：多端同产品

输入：Web 与原生桌面共用服务，用户明确要求界面效果一致；两套组件默认样式不同，原生缺少一项控件。

观察：共用页面/状态基线，登记控件实现缺口；无擅自放宽成“业务等价即可”；成对验收条件可执行。

### 场景 C：简单产品与只读请求

输入：三个页面的小工具，只要求在回复里审查功能遗漏。

观察：输出比例适当的审查，不写文件、不初始化规格、不强行拆成大量 Screen，也不套用活动管理或智能体业务。

### 场景 D：长任务和未知副作用

输入：上传后调用第三方发布，连接在提交后超时；页面有取消、重试和返回。

观察：区分接纳/执行/外部确认；超时显示未知并先对账；不把点击重试设计成重复发布；关闭页面不自动改变任务状态。

## 评测记录

记录输入、技能版本、实际输出位置、遗漏/误判、修正和复测结果。语法验证、链接验证和以上真实行为评测分别报告；不虚构分数或通过状态。

### 场景 E：已有 OpenSpec 的计划整理

输入：已有 change/tasks.md，含人工完成标记；用户要求功能、界面与后续计划按固定模式整理。

观察：交付七份固定 Markdown 与 delivery.json；任务引用原清单且保持人工状态，不另建可勾选副本。功能和 Surface 均映射任务，依赖无环；遗漏任务、缺字段、未解决 blocker 和未完成审阅必须使完成门禁失败。

### 场景 F：文件齐全但只有几个界面拼凑

输入：七份文件和 JSON 均齐全，01 仅有“人员管理/活动管理/统计报表”三行，02 只有“Header/Sidebar/Content”，03 只有正常链，05 只有“完善页面”；用户要求按固定模式输出详细功能设计计划。

观察：即使结构验证通过，语义审阅仍失败；逐模块补齐目标、字段、权限、规则与状态，逐页补内容分区，逐操作补异常恢复，再形成任务执行说明。不得通过增加截图数量或仅改 JSON 把状态变成 ready。

### 场景 G：从真实案例迁移到新产品

输入：以 示例项目A P06 为范例整理维修工单系统，工单允许部分分派成功，尚未确定附件大小限制。

观察：复用固定展开过程，不复制活动导航、18 个 Surface、Preview→Commit 或名单原子提交规则；保留工单的部分成功语义和附件阈值待决。逐条写清真实业务依据。
